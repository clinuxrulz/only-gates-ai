Read this first

One float boundary, then integers all the way

Integer GPT is not a new architecture. It is the same decoder-only transformer with a different arithmetic contract. Training still needs floating point and gradients. Inference does not: once the weights stop changing, every operation is a fixed sequence of adds, multiplies, shifts, comparisons, and table lookups. This page teaches that sequence from the checkpoint down to the sampled token.

If you have never built a GPT before, do not skip the next nine chapters. They answer three questions in order: what a GPT computes, what each part is for, and how to implement the float version yourself. The integer chapters only make sense once that dataflow is familiar.

Why integer inference at all?

  • Size. An int8 weight is one byte instead of four. The model fits in smaller memory and moves less data.
  • Determinism. Integer operations have exact results. The same input and seed produce the same output on every machine, which is useful for tests and for hardware.
  • Portability. The engine needs only integer add, multiply, shift, compare, and table lookup. Those exist on a CPU, a GPU, a microcontroller, an FPGA, and eventually a gate-level circuit.
  • Understanding. Quantization forces you to name every scale and every shift. That makes the arithmetic auditable instead of hidden inside a float library.

The cost is accuracy and engineering effort. Quantization changes the probabilities, and every operation needs a scale and overflow argument. This page treats those costs honestly: the goal is the same decisions, not bit-identical output.

01

Foundations · the math

The small amount of math a GPT actually uses

You do not need calculus, statistics, or a machine-learning course to read this page. A GPT is built from five ideas: vectors, dot products, matrix multiplication, a normalizing function called softmax, and derivatives used during training. Everything else is bookkeeping. This chapter defines those ideas in the order you will meet them.

Numbers, vectors, and matrices

A scalar is one number, such as 3.5. A vector is an ordered list of numbers, such as [1.0, -2.0, 0.5]. A matrix is a rectangular grid of numbers. In this tutorial, a vector is a row (or a column) and a matrix is a table of rows.

The model constantly uses vectors to represent one token at one position. If a vector has D numbers, we say the model dimension is D. The numbers inside the vector are not individually labelled “noun” or “colour”; training chooses them so that useful distinctions become easy for later operations to read.

The notation used in every later chapter
NotationMeaningExample

A matrix is stored in memory as a flat list, row by row. The value at row i and column j of a matrix with cols columns lives at index i * cols + j. That single fact explains most pointer arithmetic in the C engine.

The dot product measures agreement

A dot product multiplies two equal-length vectors element by element and adds the results:

u · v = Σ u[i] · v[i]

[1, 2, 3] · [4, 5, 6]
  = 1·4 + 2·5 + 3·6
  = 4 + 10 + 18
  = 32

If two vectors point in similar directions, their dot product is large and positive. If they are unrelated, the positive and negative products cancel and the result is near zero. If they point in opposite directions, the result is negative. Attention and the output head both use the dot product as a similarity score.

Matrix multiplication is many dot products

Multiplying matrix A (shape [m, k]) by matrix B (shape [k, n]) produces C (shape [m, n]). Each output cell is one dot product: row i of A against column j of B.

C[i][j] = Σ A[i][k] · B[k][j]

A = [1 2 3]      B = [ 7  8]
    [4 5 6]          [ 9 10]
                     [11 12]

C = [1·7 + 2·9 + 3·11   1·8 + 2·10 + 3·12]  = [ 58   64]
    [4·7 + 5·9 + 6·11   4·8 + 5·10 + 6·12]    [139  154]

One matrix multiply can compute thousands of dot products at once. That is why nearly all of a GPT’s compute is matrix multiplication. The integer engine replaces the float multiply-add with an int8 multiply and an int32 accumulate, but the shape of the operation is identical.

Exponentials and softmax

exp(x), written eˣ, turns any real number into a positive number. It is 1 at x = 0, grows quickly for positive inputs, and approaches 0 for negative inputs. Softmax uses it to turn a list of arbitrary scores into a probability distribution:

softmax(z)[i] = exp(z[i]) / Σ exp(z[j])

softmax([2, 1, 0])
  = [7.389, 2.718, 1.000] / 11.107
  = [0.665, 0.245, 0.090]

The outputs are positive and sum to 1.0.

The largest score gets the most probability mass, but the others still receive some. A temperature divides the scores before softmax and changes how sharp the result is; chapter 07 explains that in detail. In the integer engine, the exponential becomes a small lookup table and the division becomes an integer normalization.

Averages, square roots, and logarithms

Three more functions appear often:

  • Mean: add the values and divide by the count. The average of [1, 3, 5] is 3.
  • Root mean square: square each value, take the mean, then take the square root. For [3, 4] the squares are [9, 16], the mean is 12.5, and the RMS is about 3.536. RMSNorm uses this to measure the size of a vector.
  • Natural logarithm: the inverse of exp. log(1) = 0, log(e) = 1, and log(0.1) ≈ -2.303. Training uses -log(probability) as the loss; a confident correct prediction has a small loss, and an unlikely correct prediction has a large loss.

Slopes, gradients, and the chain rule

A derivative answers: if I nudge this input a little, how much does the output move? For f(x) = x², the derivative is 2x. At x = 3, a tiny increase in x increases f about six times as fast.

Training adjusts every weight in the direction that lowers the loss. The gradient is the vector of derivatives with respect to all weights. The chain rule says that for composed functions you multiply the local slopes. For example, if y = w·x and loss = (y - target)², then

d loss / d w = 2 · (w·x - target) · x

Backpropagation is just the chain rule applied through every operation in the network, from the loss backwards to each weight. You do not have to derive it by hand to use the trainer, but knowing what a gradient is makes the training chapter readable.

Why this matters for integers. Every operation above is either exact integer arithmetic (add, multiply, compare, shift) or a function that can be approximated by a table (exp, square root, GELU). The model’s behaviour is fixed once training ends, so inference can replace the float versions with integer versions that are close enough for the same decisions to survive.

02

Foundations · the idea

A GPT is a next-token probability machine

Strip away the marketing and a GPT is one function. You give it a sequence of tokens, and it returns a score for every token in its vocabulary. The score says how likely that token is to come next. That is the entire model. Generation is a loop around this function:

  1. Turn the prompt into token ids.
  2. Run the model on the current window of ids.
  3. Get one probability for every token id in the vocabulary.
  4. Choose a token, usually by sampling from that distribution.
  5. Append the token and repeat until a stop condition.

What the letters mean

GPT is an acronym plus an architecture
WordMeaningIn this project
GenerativeIt produces new tokens one at a timeA generation loop in the host
Pre-trainedWeights were learned from text before any fine-tuningAn LM stage, then a Q&A stage
TransformerThe block stack that processes the tokensPre-norm, attention, and an MLP per block
Decoder-onlyEach position may only look at itself and earlier positionsThe causal mask in attention

“Decoder-only” matters for generation. The model is trained to predict the next token from the tokens before it. It is never allowed to look at the future during training, because at generation time there is no future yet. The rest of the architecture exists to make that prediction accurate and trainable.

A concrete example

Suppose the vocabulary is only four tokens: sky, blue, dark, and cloud. After reading the prompt “the sky is”, the model might return:

blue   0.62
dark   0.18
cloud  0.14
sky    0.06

The model has not looked up a fact. It has computed a vector for the current position and compared it with every token’s embedding. The comparison produces four logits, softmax turns them into probabilities, and the host samples one. A different sample can produce a different sentence, which is why temperature and top-k exist.

The model has no memory between calls. A chat appears to remember because the host sends the whole conversation back every time. The context window is the model’s entire working memory. Once the conversation is longer than the window, the oldest tokens are dropped.

Parameters are the learned numbers

A parameter (or weight) is a number that training adjusts. A GPT is mostly a pile of matrices full of parameters, plus a few vectors. The tiny models on this page have 62,448 and 264,528 parameters. Large language models have billions, but the operations are the same; only the shapes and the amount of compute change.

The weights encode statistical regularities, not a database of facts. That is why a model can be fluent and confidently wrong at the same time. It is also why changing the tokenizer without changing the weights produces valid arithmetic and meaningless text: the ids no longer mean the same thing.

Why a transformer?

A simpler model could predict the next token from a fixed window using only a matrix multiply. The transformer adds two mechanisms that make long-range prediction much better:

  • Attention lets each position pull information from earlier positions, so a pronoun can use the noun it refers to and a question can use the whole prompt.
  • The MLP gives each position a nonlinear computation of its own, so the model can combine features instead of only averaging them.

Stack those two mechanisms in a residual stream, repeat the block a few times, and normalize the result. That is the entire architecture. Chapters 04 to 07 explain each part and what it is for.

Training versus inference

03

Foundations · the input

Tokens, token ids, and the embedding lookup table

A neural network cannot read characters. It reads integers. A tokenizer is the separate program that turns text into a sequence of token ids. A token is a chunk of text: a word, part of a word, a byte, or a special marker. The set of all tokens the model knows is its vocabulary, of size V.

Three common tokenizers

The tokenizer choice is a modeling decision
KindHow it splits textVocabularyUsed here
CharacterOne token per characterSmallRarely
Word-levelOne token per word, unknown words share a tokenSmall to mediumAlice, V=512
Byte-level BPEStarts from bytes and merges common pairsMediumSolid 2, V=4096

BPE stands for byte-pair encoding. It starts with individual bytes and repeatedly merges the most frequent adjacent pair into a new token. The result is a vocabulary that can represent any byte sequence while using longer tokens for common words. The details do not matter for the forward pass; the engine only ever sees ids.

Special tokens are ordinary vocabulary entries with reserved ids. This project uses <pad> for padding, <bos> for the beginning of a sequence, <eos> for the end, and chat markers such as <|user|> and <|assistant|>. They let the host tell the model where a turn starts and stops.

An id is an index, not a quantity

Token id 400 is not “twice as much” as token id 200. The id is only a row number in a table. The table is called the token embedding. It has one row per vocabulary entry, and each row has D numbers:

token_emb: shape [V, D]
row for token id 2: [0.5, 0.1, -0.3]

x = token_emb[2]

The embedding row is learned. At the start of training it is random. By the end, tokens that need similar treatment tend to have rows that produce similar scores in later operations. Nobody assigns the meaning of each coordinate by hand.

Position embeddings tell the model where it is

Attention and the MLP are otherwise blind to order: they see a set of token vectors. To distinguish “dog bites man” from “man bites dog”, the model adds a second learned vector that depends on the position in the window:

pos_emb: shape [T, D]

x[t] = token_emb[tokens[t]] + pos_emb[t]

The addition works because both vectors have the same width and the model can learn to separate the two signals. This project uses a learned absolute position table. Other models use rotary or relative positions; the integer engine keeps the simpler table because it is easier to quantize and cheaper to run.

A complete embedding example

The output X is the input to the first transformer block. It has one row per position and one column per model dimension. Every later operation reads and writes matrices with the same [T, D] shape, with a few detours into [T, 3D] for attention and [T, M] for the MLP.

The context window

T is fixed at training time. The model has a position embedding for each slot and is trained on windows of exactly that length. At inference the host must therefore supply exactly T ids: it pads short prompts and keeps only the last T ids of long ones. This project left-pads so the newest token sits in the last slot.

A checkpoint and a tokenizer are a pair. weights.bin does not contain the tokenizer. If you load a checkpoint with the wrong vocabulary, every id maps to a different embedding row, and the model produces confident nonsense. Always ship the tokenizer next to the weights.

What the integer engine stores

The C engine stores token_emb as int8 codes with one Q16 scale per row, and pos_emb as int8 codes with one Q16 scale per row. Embedding a token is a table lookup, a multiply by the row scale, and an add. The scale is what turns a small integer code back into a useful real number. Chapter 13 explains how those scales are chosen.

04

Foundations · the parts

The transformer block: what each part is for

A GPT is a stack of identical transformer blocks. Each block reads a matrix of shape [T, D] and writes a matrix of the same shape. Nothing is added or removed: the block only changes the numbers in place. That fixed shape is why blocks can be stacked L times without special cases.

The shared matrix is called the residual stream. Think of it as a shared notebook with one row per token position. Each part of the block reads the notebook, computes something useful, and writes an update back into the same row. A part never replaces the notebook; it adds to it.

The four parts and their jobs

Why a transformer block contains exactly these pieces
PartInput → outputJobIf you removed it
RMSNorm[T, D] → [T, D]Rescale each row to a stable size before a learned operationActivations drift in scale; training becomes unstable
Attentionnormalized [T, D] → [T, D]Move information between token positionsEach position is isolated; pronouns and questions lose context

RMSNorm: keep the numbers in a useful range

A vector’s values can become very large or very small as they pass through many layers. Large values saturate nonlinearities and make gradients unstable. RMSNorm divides each row by its root mean square, then multiplies by a learned per-dimension gain:

rms(x)     = sqrt(mean(x[i]²) + ε)
rmsnorm(x) = x / rms(x) · gain

The gain starts at 1 and is learned. ε is a tiny number
that prevents division by zero.

Unlike LayerNorm, which subtracts the mean and divides by the standard deviation, RMSNorm does not subtract the mean first. That saves an operation per row and works well in transformer language models. The integer implementation uses a Q32 epsilon and an integer square root; chapter 15 derives every scale.

Attention: move information between positions

After embedding, each position knows only its own token and position. Attention lets position t read from positions 0 … t. It does this by projecting every row into three roles: a query, a key, and a value. The query of position t is compared with the key of every allowed position; the resulting scores decide how much of each value to add to the output. Chapter 05 builds this from scratch.

The causal part is essential. Because the model is trained to predict the next token, position t must not see position t + 1. The implementation enforces this by only computing scores for j ≤ t, which is both correct and cheaper than computing the future and masking it later.

The MLP: compute within a position

Attention mixes information across positions, but it is a weighted average of value vectors, which is a mostly linear operation. The MLP (multi-layer perceptron, also called the feed-forward network) gives each position a nonlinear computation of its own. It expands the vector from D to a wider hidden size M, applies GELU, and projects back to D:

z = h · W1          # [T, D]  → [T, M]
g = GELU(z)         # elementwise, [T, M] → [T, M]
m = g · W2          # [T, M]  → [T, D]

The same MLP is applied to every row independently. It is where much of the model’s per-token feature computation happens. Chapter 06 explains the expansion, the nonlinearity, and the GELU approximation.

Residual connections: learn a change, not a replacement

Every sublayer is wrapped in a residual add:

x = x + attention(rmsnorm(x))
x = x + mlp(rmsnorm(x))

The addition has three effects. It preserves the original signal, so a later layer can always recover what an earlier layer knew. It gives the gradient a short path back through the network during training. And it means each sublayer only has to learn a small adjustment, which is easier than learning a complete replacement from scratch.

Pre-norm: normalize before, not after

The order above is pre-norm: normalize, apply the sublayer, add to the stream. Older transformers normalized after the add. Pre-norm is easier to train deeply, and it is cheaper in the integer engine because the residual stream itself is never rewritten by a norm. The engine’s block is literally the two lines above.

What one block costs

With D = 48 and M = 96, one block contains:

  • Attention: D×3D for QKV plus D×D for the output projection = 4D² = 9,216 weights.
  • MLP: D×M up plus M×D down = 2DM = 9,216 weights.
  • Norms: two gains of D = 2D = 96 weights.

So one block is 18,528 parameters. Three blocks plus the embedding tables and the final gain give the 264,528-parameter Solid 2 model. A “bigger model” mostly means more blocks and wider matrices, not a different kind of computation.

Depth is iterative refinement. Early blocks tend to build local features; later blocks can combine them. That is a useful intuition, not a strict rule. What matters for this page is that every block has the same shape and the same set of operations, which is what makes both the C engine and a hardware pipeline regular.

05

Foundations · attention

Attention from scratch: queries, keys, and values

Attention answers a simple question: which earlier positions should this position listen to? Consider “The animal did not cross the street because it was too tired.” To interpret “it”, the model needs to connect that position to “animal”. Attention is the mechanism that makes that connection.

The library analogy

Imagine a library. Your query is what you are looking for. Each book has a key on its spine describing what it contains. You compare your query with every key to see which books are relevant. Then you read the value, the actual content, and combine the relevant books in proportion to their relevance.

In a transformer, every position emits all three:

  • Query (Q): what this position is looking for.
  • Key (K): what this position can offer to others.
  • Value (V): the information this position passes on when selected.

Q, K, and V are not hand-written. They are three learned linear projections of the same normalized row. The model learns which directions in the vector space should act as questions, which as labels, and which as content.

The formula, one piece at a time

Q = h · Wq        # [T, D]
K = h · Wk        # [T, D]
V = h · Wv        # [T, D]

scores = Q · Kᵀ / sqrt(head_dim)     # [T, T]
scores[j > t] = -∞                   # causal mask
P = softmax(scores, axis=keys)       # [T, T]
out = P · V                          # [T, D]
  • Why divide by sqrt(head_dim)? A dot product over d dimensions has variance that grows with d. Without the scale, scores become large, softmax saturates, and gradients vanish. Dividing by sqrt(d) keeps the scores in a useful range.
  • Why softmax over keys? Each query produces one score per allowed key. Softmax turns that row into non-negative weights that sum to one, so the output is a weighted average of values.
  • Why the causal mask? During training the model sees the whole sequence but must predict each next token using only the past. Setting future scores to negative infinity gives them zero probability. At generation time those positions do not exist yet, so the same rule is both necessary and natural.

A two-token worked example

Position 0 keeps only its own value because it has no past. Position 1 mixes both values, with more weight on the key that matches its query. With learned weights the pattern is richer, but the mechanics are exactly this.

Multi-head attention

One attention pattern can only express one kind of relationship. A head is an independent attention computation on a slice of the vector. With H heads, each head has width head_dim = D / H. Every head has its own Q, K, V projections, computes its own scores and weighted sum, and the results are concatenated back to width D. A final output matrix Wo mixes the heads.

Different heads can learn different jobs: one may track nearby tokens, another may connect a pronoun to a noun, another may copy a delimiter. The model is not told which is which; the split is learned. In this project Solid 2 has D = 48 and H = 4, so each head is 12 numbers wide.

What is learned here

The only learned parameters are Wq, Wk, Wv, and Wo. In the C engine the three input projections are fused into one [D, 3D] matrix called wqkv. That saves two matrix multiplies and one pass over the input. The math is exactly the same; only the storage layout changes.

Attention is not a database lookup. The weights are computed from the current vectors, so the same key can be relevant in one context and irrelevant in another. The dot product is a learned similarity measure, not an exact match.

Foundations · the MLP

The MLP and GELU: where each token is transformed

Attention is good at moving information between positions. It is less good at computing with that information, because its output is a weighted average of value vectors, which is close to linear. The MLP is the nonlinear computation that follows. It runs independently on every position, so it never mixes tokens.

z = h · W1          # expand:  [T, D] → [T, M]
g = GELU(z)         # nonlinear: [T, M] → [T, M]
m = g · W2          # contract: [T, M] → [T, D]

x = x + m           # residual add, back in the stream

The same matrix W1 is applied to every row, then the same GELU, then the same W2. A position’s row never sees another position’s row inside the MLP. That is the clean division of labour: attention communicates, the MLP computes.

Why expand the width?

The up-projection gives the model a wider space in which to combine features before compressing back. The original transformer used M = 4D; this project uses M = 2D (96 for D = 48) to keep the tiny model small. A wider hidden layer means more parameters and more compute, but also more capacity to represent intermediate combinations.

The cost is 2DM weights per block: D×M for the up-projection and M×D for the down-projection. For Solid 2 that is 9,216 parameters per block, the same as the entire attention block.

Why the nonlinearity is not optional

Suppose GELU were removed. Then the whole MLP would be:

m = (h · W1) · W2 = h · (W1 · W2)

Two linear maps in a row are just one linear map. No matter how many layers you stack, the model could only represent a single linear transformation of the input. The nonlinearity breaks that collapse and lets the network represent curved, conditional relationships. Attention needs its own nonlinearity for a different reason: without softmax, the weights would not be normalized, so the mix of values would not be a stable, bounded average. GELU and softmax are the two nonlinearities that make a deep transformer more than a stack of matrix multiplies.

What GELU looks like

GELU stands for Gaussian error linear unit. This project uses the tanh approximation:

GELU(x) = 0.5 · x · (1 + tanh(0.79788456 · (x + 0.044715 · x³)))

Its shape is simple to describe:

  • For large positive x, it is almost the identity: GELU(3) ≈ 2.996.
  • At zero it is zero: GELU(0) = 0.
  • For small negative x, it becomes slightly negative: GELU(-1) ≈ -0.159.
  • For large negative x, it approaches zero: GELU(-3) ≈ -0.004.

So GELU acts like a smooth gate: it lets positive evidence through, suppresses strong negative evidence, and keeps a small negative channel near zero. It is smooth, which makes it easy to approximate with a lookup table. Chapter 16 builds the 1,025-entry integer table.

A tiny numeric picture

Take one position with D = 2, M = 3, and a hidden row h = [1, -1]. Let the up-projection produce z = [1, -1, 0]. After GELU:

z      = [ 1.000, -1.000,  0.000]
GELU(z)= [ 0.841, -0.159,  0.000]

The down-projection then mixes those three numbers back into two. The exact result depends on W2, but the important part is that the negative value was not simply deleted; it was scaled to -0.159 and can still contribute.

Why this is easy to quantize

The MLP is two matrix multiplies and one elementwise function. The matrix multiplies use the same integer kernel as every other linear layer. GELU is the only difficult part, and because its input is bounded in practice, the engine can precompute it at load time into a Q16 table and interpolate. There is no tanh call in the forward pass.

Foundations · the output

Logits, softmax, temperature, and sampling

After the last block, the model has a [T, D] matrix. Only the last row matters for generation, because it is the position that predicts what comes next. The final steps turn that row into a token id.

  1. Normalize the last row with the final RMSNorm gain.
  2. Multiply by the output head to get one score per vocabulary token.
  3. Divide by temperature and apply softmax to get probabilities.
  4. Optionally keep only the top-k tokens and renormalize.
  5. Draw a token from the distribution (or take the argmax).

The output head and tied embeddings

The output head is a matrix of shape [D, V]. Multiplying the normalized row [1, D] by it produces [1, V] logits: one unbounded score per vocabulary token.

logits = final_norm(x) · head

In this project the head is not a separate learned matrix. It is the token embedding matrix transposed, so the logit for token id is the dot product between the final hidden vector and that token’s embedding row. The model is asking: “how compatible is this position with token id?” This is called tied embeddings. It saves V·D parameters and keeps the input and output token spaces aligned.

Softmax turns scores into probabilities

Logits can be negative, large, or small. Softmax exponentiates them and divides by the sum, producing positive probabilities that sum to one:

p[i] = exp(logit[i]) / Σ exp(logit[j])

logits = [2, 1, 0]
exp    = [7.389, 2.718, 1.000]     sum = 11.107
p      = [0.665, 0.245, 0.090]

In practice the implementation subtracts the maximum logit before exponentiating. That changes nothing mathematically, because the same factor cancels in the division, but it prevents exp from overflowing for large logits. The integer engine does the same thing with a Q12 delta and a table.

Temperature changes the shape, not the order

Temperature τ divides the logits before softmax:

p[i] = exp(logit[i] / τ) / Σ exp(logit[j] / τ)

same logits [2, 1, 0]

τ = 1.0  → [0.665, 0.245, 0.090]
τ = 0.5  → [0.867, 0.117, 0.016]
τ = 2.0  → [0.506, 0.307, 0.186]

Lower temperature sharpens the distribution toward the top choice. Higher temperature flattens it toward uniform. Temperature never changes which token has the highest probability; it only changes how often the others are chosen. At τ → 0 the result approaches greedy decoding. The engine clamps the temperature to a small positive floor so it never divides by zero.

Top-k

Top-k keeps only the k highest-probability tokens, sets the rest to zero, and renormalizes. It prevents the sampler from occasionally choosing a token from the long tail. For a 4,096-token vocabulary, k = 40 is a common choice. The sampler in this engine uses a small insertion sort to find those 40 candidates.

Sampling versus greedy decoding

Greedy decoding always takes the argmax. It is deterministic and often repetitive. Sampling draws a random number in [0, 1) and walks the cumulative probabilities until it crosses that number. A token with probability 0.6 occupies 60% of the interval, so it is chosen about 60% of the time.

p = [0.6, 0.3, 0.1]
cumulative = [0.6, 0.9, 1.0]

r = 0.42  → token 0
r = 0.75  → token 1
r = 0.97  → token 2

The engine implements this with integer weights and a 32-bit xorshift generator. Given the same seed and the same probabilities, it returns the same token, which makes tests reproducible. Chapter 19 covers the exact integer arithmetic.

Putting the loop together

ids = tokenize(prompt)
while not done:
    window = last_T_ids(ids, pad=pad_id)
    logits = model(window)[-1]          # last position only
    probs  = softmax(logits / temperature)
    probs  = top_k(probs, k)
    next   = sample(probs, seed)
    if next is stop_token: break
    ids.append(next)
return detokenize(ids)

That is the whole generation algorithm. The model is called once per output token in this project, because there is no KV cache. The next chapters replace each line with the exact integer implementation.

Why the model does not “decide” to stop. The stop token is just another token in the vocabulary. If it has the highest probability, or is sampled, generation stops. The host enforces the stop condition by checking the returned id, not by asking the model.

Foundations · learning

How training turns random numbers into a language model

At the start of training, every weight is random. The model produces nonsense. Training is the process that repeatedly measures how wrong the model is and nudges every weight in the direction that makes it slightly less wrong. That is the whole idea; the rest is engineering.

Step 1: turn text into training examples

The corpus is tokenized into one long stream of ids. A training example is a window of T ids plus the same window shifted by one:

stream = [the, cat, sat, on, the, mat, ...]

input  = [the, cat, sat, on]
target = [cat, sat, on, the]

At every position, the target is the token that came next. One window therefore provides T prediction problems at once. The model is not trained on a separate “what is a noun” task; next-token prediction is the only objective, and useful internal representations emerge because they help predict the next token.

Step 2: measure the error with cross-entropy

The forward pass produces a probability for every vocabulary token at every position. The loss looks only at the probability assigned to the correct next token:

loss = -log( p[target] )

p[target] = 0.90  → loss = 0.105
p[target] = 0.10  → loss = 2.303
p[target] = 1/4096 → loss = 8.317  (random guessing)

This is called cross-entropy loss. It punishes confident wrong answers much more than uncertain ones. The average loss over many examples is a single number that training tries to minimize.Perplexity is exp(loss); it is roughly “how many equally likely tokens is the model choosing between?”

Step 3: compute gradients

For every parameter, the gradient says how the loss would change if that parameter increased slightly. Backpropagation computes all of them efficiently by applying the chain rule from the loss backwards through the network. In PyTorch this is one call:

loss.backward()   # fills param.grad for every parameter

You do not write a separate gradient formula for attention, RMSNorm, and GELU. The autograd system records the forward operations and applies the chain rule automatically. This is why the training code can be short even though the model is deep.

Step 4: update the weights

Plain gradient descent moves each weight against its gradient:

w = w - learning_rate · gradient

The learning rate controls the step size. Too large and training diverges; too small and it takes forever. This project uses AdamW, which keeps a running average of the gradient and of the squared gradient for each parameter, and scales the update accordingly. AdamW also applies a small weight decay that discourages unnecessarily large weights.

A step is one optimizer update. A batch is the group of windows used to compute one gradient. An epoch is one pass over the training set. The learning rate usually follows a warmup and cosine schedule: it rises briefly at the start, then decays smoothly.

Training versus validation

If you only measure loss on the training data, a small model can memorize it and look perfect while failing on new text. That is overfitting. The trainer therefore holds out a validation set. Training loss should fall; validation loss should fall too, at least for a while. When validation loss starts rising while training loss keeps falling, the model is memorizing.

Dropout randomly zeros some activations during training to make memorization harder. It is disabled at inference, which is why the C engine has no dropout code at all. The exported model is the deterministic version.

Why training cannot be integer-only

Gradients are tiny, signed, and change magnitude constantly. AdamW keeps running averages that also need a wide dynamic range. Training does not “store” the text. It adjusts parameters to reduce prediction error on the text. A small model trained on a few documents will reproduce patterns from those documents, but it is not a searchable database. This is also why evaluation needs held-out prompts, not just prompts copied from the training set.

import numpy as np

def rmsnorm(x, gain, eps=1e-5):
    """x: [T, D] -> [T, D]"""
    return x / np.sqrt((x * x).mean(axis=-1, keepdims=True) + eps) * gain

def softmax(x, axis=-1):
    x = x - x.max(axis=axis, keepdims=True)
    e = np.exp(x)
    return e / e.sum(axis=axis, keepdims=True)

def gelu(x):
    return 0.5 * x * (1.0 + np.tanh(
        0.7978845608028654 * (x + 0.044715 * x ** 3)
    ))

def attention(h, layer, heads):
    """h: [T, D]; weights use the C engine's [in, out] layout."""
    T, D = h.shape
    head_dim = D // heads

    qkv = h @ layer["wqkv"]                 # [T, 3D]
    q, k, v = np.split(qkv, 3, axis=-1)     # each [T, D]

    # Split the model dimension into heads: [T, D] -> [H, T, head_dim]
    q = q.reshape(T, heads, head_dim).transpose(1, 0, 2)
    k = k.reshape(T, heads, head_dim).transpose(1, 0, 2)
    v = v.reshape(T, heads, head_dim).transpose(1, 0, 2)

    scores = q @ k.transpose(0, 2, 1) / np.sqrt(head_dim)  # [H, T, T]

    # Causal mask: position t may only see keys j <= t.
    mask = np.triu(np.ones((T, T), dtype=bool), k=1)
    scores = np.where(mask, -np.inf, scores)

    probs = softmax(scores, axis=-1)         # [H, T, T]
    out = probs @ v                          # [H, T, head_dim]
    out = out.transpose(1, 0, 2).reshape(T, D)
    return out @ layer["wo"]                 # [T, D]

def forward(tokens, p):
    """tokens: list of token ids; p: dict of [in, out] weights."""
    T = len(tokens)
    x = p["token_emb"][tokens] + p["pos_emb"][:T]   # [T, D]

    for layer in p["blocks"]:
        h = rmsnorm(x, layer["g1"])
        x = x + attention(h, layer, p["heads"])

        h = rmsnorm(x, layer["g2"])
        x = x + gelu(h @ layer["w1"]) @ layer["w2"]

    h = rmsnorm(x, p["g_final"])
    return h @ p["token_emb"].T              # [T, V] logits

Read it in the same order as the model

  1. Embed. Look up one row per token, add one position row, and get [T, D].
  2. For each block: normalize, project to Q/K/V, split into heads, score, mask, softmax, mix values, project out, add to the residual.
  3. Then: normalize again, expand to M, apply GELU, contract back to D, add to the residual.
  4. Finally: normalize with the last gain and multiply by the transposed embedding table to get [T, V] logits.

Porting the reference to C

  • Replace each matrix with a flat array and a shape. Row-major indexing is row * cols + col.
  • Replace each float multiply-add with the integer matmul: quantize the activation row, accumulate int8 products in int32, requantize in int64.
  • Replace sqrt with int_isqrt_u64, exp with exp_neg_q15_q12, and GELU with the lookup table.
  • Keep the same loop order and the same residual adds. If a result differs, compare the first buffer that diverges, not the final logits.
  • Test the tiny identity model first. A model with known outputs is easier to debug than a trained one.
Why start from a reference? The C engine has no automatic differentiation, no shape checks, and no exceptions. A float reference gives you a trusted set of expected numbers. Without it, every integer bug looks like a model bug and every model bug looks like a quantization bug.

The shape of the thing

A decoder-only transformer small enough to hold in your head

Both models on this page are the same architecture at two sizes. Tokens become learned embeddings, pass through pre-norm blocks, and are projected back onto the vocabulary with the same embedding matrix. There are no biases, no LayerNorm, no learned position table beyond the small embedding, and no operator that lacks an integer implementation.

Before reading the table, keep one picture in mind: the model holds a matrix with one row per token position and one column per feature. That matrix is called the residual stream. Every layer reads it and writes an update back into it. The six numbers below are the only dimensions you need to follow that matrix through the engine.

  • V is the vocabulary size: how many different token ids exist. It is the number of rows in the embedding table and the number of outputs from the final head.
  • T is the context length: how many positions the model reads at once. Every activation matrix has T rows.
  • D is the model width: how many numbers represent one token at one position. It stays constant through every block.
  • L is the number of identical transformer blocks stacked after the embedding.
  • H is the number of attention heads. Each head works on D/H numbers.
  • M is the hidden width inside the MLP. It is usually wider than D so the model can combine features before projecting back.

The parameter count is V·D + T·D + D + L·(2D + 4D² + 2D·M). The first three terms are the token table, position table, and final norm gain. Each block has two norm gains of size D, a D×3D QKV matrix, a D×D output matrix, a D×M up-projection, and an M×D down-projection. For Solid 2 that is 264,528 values, or about 1.06 MB as float32.

Read the formula as four separate purchases. The embedding table costs V·D because every token needs a D-number vector. Positions cost T·D for the same reason. Each block spends 2D on its two norm gains, 4D² on attention (three input projections plus one output projection), and 2DM on the MLP. Nothing is hidden: the parameter count is exactly the sum of the matrix shapes you will allocate.

A bias is an extra learned vector added after a matrix multiply, one value per output. This model has none. That removes an add and a second set of parameters from every linear layer, and it means a layer is exactly “multiply by a matrix” with no hidden offset. It is a deliberate simplification for the integer engine, not a requirement of transformers in general.

class RMSNorm(nn.Module):
    def __init__(self, dim: int):
        super().__init__()
        self.gain = nn.Parameter(torch.ones(dim))

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        return x * torch.rsqrt(x.pow(2).mean(dim=-1, keepdim=True) + 1e-5) * self.gain

class Block(nn.Module):
    def __init__(self, dim: int, heads: int, mlp: int, dropout: float):
        super().__init__()
        if dim % heads:
            raise ValueError("dim % heads != 0")
        self.heads, self.head_dim = heads, dim // heads
        self.g1, self.g2 = RMSNorm(dim), RMSNorm(dim)
        self.wqkv = nn.Linear(dim, dim * 3, bias=False)
        self.wo = nn.Linear(dim, dim, bias=False)
        self.w1 = nn.Linear(dim, mlp, bias=False)
        self.w2 = nn.Linear(mlp, dim, bias=False)
        self.dropout = nn.Dropout(dropout)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        B, T, D = x.shape
        h = self.g1(x)
        qkv = self.wqkv(h).view(B, T, 3, self.heads, self.head_dim)
        q, k, v = qkv.unbind(2)
        q, k, v = q.transpose(1, 2), k.transpose(1, 2), v.transpose(1, 2)
        scores = (q @ k.transpose(-2, -1)) / math.sqrt(self.head_dim)
        mask = torch.triu(torch.ones(T, T, dtype=torch.bool), 1)
        scores = scores.masked_fill(mask, float("-inf"))

            self.wo((torch.softmax(scores, -1) @ v).transpose(1, 2).reshape(B, T, D))
        )

        self.pos_emb = nn.Embedding(ctx, dim)
        self.blocks = nn.ModuleList(
            [Block(dim, heads, mlp, dropout) for _ in range(layers)]
        )
        self.g_final = RMSNorm(dim)
        self.apply(self._init)
        for b in self.blocks:
            nn.init.normal_(b.wo.weight, std=0.02 / math.sqrt(2 * max(1, layers)))
            nn.init.normal_(b.w2.weight, std=0.02 / math.sqrt(2 * max(1, layers)))

    @staticmethod
    def _init(m):
        if isinstance(m, (nn.Linear, nn.Embedding)):
            nn.init.normal_(m.weight, 0.0, 0.02)

    def forward(self, tokens, targets=None):
        B, T = tokens.shape
        if T > self.context:
            raise ValueError("seq > context")
        x = self.token_emb(tokens) + self.pos_emb(torch.arange(T, device=tokens.device))
        for b in self.blocks:
            x = b(x)
        logits = self.g_final(x) @ self.token_emb.weight.T
        loss = None
        if targets is not None:
            loss = F.cross_entropy(
                logits.reshape(-1, self.vocab_size),
                targets.reshape(-1),
                ignore_index=-100,
            )
        return logits, loss

Why the forward pass is shaped this way

  • Pre-norm. h = RMSNorm(x), then attention or MLP, then x = x + sublayer(h). The integer engine can reuse the same residual buffer without a separate normalization pass at the end of the block.
  • No biases. Every linear layer is a matrix multiply. That removes an add and a second scale from every output.
  • GELU tanh. The tanh approximation is smooth and bounded, which makes it a good lookup table. The exact erf form would need a wider table for the same error.
  • Tied embeddings. The final projection is g_final(x) @ token_emb.weight.T. The C loader can build the transposed head once and reuse the embedding scales.
  • Learned absolute positions. A T×D table is added to the token embeddings. No rotary or ALiBi path is needed, which keeps the integer engine smaller.

  1. token_emb · V×D
  2. pos_emb · T×D
  3. g_final · D
  4. for each layer: g1, wqkv, wo, g2, w1, w2

Fixed-point foundations

Q formats, rounding, and the overflow budget

A fixed-point number is an integer plus a contract about where the binary point sits. Q16 means “divide by 65536 to get the real value.” Q15 means “divide by 32768.” Q12 means “divide by 4096.” There is no exponent, no NaN, and no denormal. The contract is the whole type.

Think of money. If every price is stored in cents, a value of 1234 means $12.34 and the “scale” is 100. Q16 is the same idea with a scale of 65536: the integer 65536 means 1.0, 32768 means 0.5, and -16384 means -0.25. Addition and subtraction work directly on the stored integers. A multiply produces twice as many fractional bits, so it needs a shift to return to the original scale.

real value = stored integer / 2¹⁶

1.0    →  65536
0.5    →  32768
0.25   →  16384
-0.25  → -16384

0.5 + 0.25 = 32768 + 16384 = 49152 = 0.75
0.5 · 0.25 = (32768 · 16384) >> 16 = 8192 = 0.125

Why not use floats everywhere? A float stores an exponent, a mantissa, and special cases; an integer multiply is simpler, smaller, and easier to map to hardware. The cost is that the range and precision are fixed in advance, so every operation must be checked against an overflow budget. This chapter does that checking once, so the rest of the engine can use plain integer operations.

Rounding is not an implementation detail

Two different rounding helpers are used, and they do not have the same tie behavior:

  • int_div_round(a, b) computes round(a / b) with ties away from zero. It works for negative numerators because it negates, adds half, divides, and negates back.
  • int_shift_round(a, shift) adds half of the divisor and then performs an arithmetic right shift. For negative exact halves, the result rounds toward +∞, not away from zero. That is acceptable for model arithmetic, but a port must copy the behavior if it wants identical bytes.

Integer square root

RMSNorm needs sqrt(mean of squares). The engine uses the classic bit-by-bit integer square root: start with the highest power of four below the input, then subtract and shift. It returns the floor of the square root, uses only integer arithmetic, and works for the full 64-bit range.

Why Q32 in RMSNorm? An activation is Q16. Squaring it gives Q32. Summing and dividing by the width stays Q32. The square root of a Q32 value is Q16, which is exactly the scale of the activation stream. The epsilon is also stored in Q32: round(1e-5 · 2³²) = 42950. That is why the code adds 42950 to the mean before taking the root.

The one float file

Turn a checkpoint into int8 codes and Q16 scales

Quantization is not “round everything to a whole number.” Each value is stored as a signed int8 code and interpreted through a scale: real ≈ code · scale / 65536. The scale is chosen from the largest magnitude in a group, so the code uses the full -127 … 127 range without overflowing.

real values:  [ 0.50, -0.25,  0.10 ]
max |value|:   0.50
scale       =  ceil(0.50 · 65536 / 127) = 259
codes       =  round(real · 65536 / scale)
            =  [ 127, -63,  25 ]

restore: code · 259 / 65536
       =  [ 0.502, -0.249,  0.099 ]

The restored values are close but not identical. The maximum error is about half a code, or scale / 2 / 65536 ≈ 0.002. That is the trade: one byte per value in exchange for a small, bounded rounding error. With one scale per column or per row, a single large value cannot force every other value in the matrix to round to zero.

The scalar helpers

q16_from_float clamps to the int32 range after multiplying by 65536. scale_q16_from_float rejects non-positive scales and never returns zero, because a zero scale would make dequantization meaningless. quantize_value rounds and clamps to -127 … 127; the code deliberately does not use -128, which keeps symmetric multiplication and negation simple.

Per-column weights

A linear layer computes one output per column. Giving every column its own scale means a single large weight in column 7 does not force every other column to use a tiny scale. The transpose in the exporter ensures that “column” in the C matrix is “output feature” in PyTorch.

Per-row embeddings

An embedding lookup returns one entire row, so the row is the natural quantization group. The tied output head reuses those exact row scales: when the embedding row is copied into the transposed head column, its scale becomes the column scale.

Gains and the head transpose

The GELU table and the head-dimension reciprocal

The GELU table has 1025 entries from -16 to 16 in steps of 1/32. Each entry is a Q16 value. That is 4,100 bytes, small enough to live in on-chip memory and cheap enough to build at load. The attention reciprocal is also computed once: inverse_sqrt_q16(head_dim) returns round(65536 / sqrt(head_dim)) using the integer square root.

The heart of the engine

int8 dot products, int32 accumulation, int64 requantization

Every linear layer is the same operation: quantize one Q16 activation row to int8, dot it against every int8 weight column, accumulate in int32, then multiply by the two scales in int64 and shift back to Q16.

The derivation

Let x = qx · sx / 2¹⁶ and w = qw · sw / 2¹⁶. Then

y = Σ x·w
  = Σ (qx·qw) · sx·sw / 2³²
  = acc · sx·sw / 2³²

The engine stores y in Q16, so:
y_q16 = y · 2¹⁶ = acc · sx·sw / 2¹⁶

That is the entire justification for the single >> 16 at the end of matmul_q16. The activation scale sx is in Q16 units, so it is not itself divided by 65536; the weight scale sw is a Q16 fraction, so it is.

Dynamic row quantization

There are two regimes. If every value fits in -127 … 127, the row is already small enough to use directly and the scale is 1. Otherwise the scale is ceil(max_abs / 127), and each code is round(value · 127 / max_abs). The first regime is not a rounding shortcut: the source values are Q16 integers, so a code of 100 with scale 1 means “100 Q16 units,” and the final shift handles the rest.

The matmul

What the two functions do, line by line

  1. Find the largest magnitude in the row. This one number decides the scale. A zero row returns scale 0 and all-zero codes.
  2. Choose a regime. If the maximum is at most 127, the Q16 values already fit in an int8 and the scale is 1. Otherwise the scale is ceil(max_abs / 127), which is the smallest integer that maps the maximum to 127.
  3. Quantize each value. Multiply by 127, divide by the maximum with rounding, and clamp to -127 … 127.
  4. For each output column, walk the input row. The accumulator is an int32 sum of int8 products. The weight index is k * out_cols + j because the matrix is stored [in, out].
  5. Requantize once. Convert the accumulator to int64, multiply by the activation scale and the weight scale, and shift by 16 with rounding. That produces one Q16 output value.

There is exactly one shift per output, not one per product. That is the efficiency win: the inner loop stays in 32-bit integer arithmetic and only the scale correction needs 64 bits. It is also the part a hardware implementation can pipeline cleanly.

A worked example

Take a Q16 activation row [65536, 32768], which is [1.0, 0.5]. The maximum is 65536, so the activation scale is (65536 + 63) / 127 = 516 and the codes are [127, 64]. Take an int8 weight column [64, -32] with Q16 scale 1024, which is [1.0, -0.5].

acc = 127·64 + 64·(-32) = 8128 - 2048 = 6080
product = 6080 · 516 · 1024 = 3,212,574,720
y_q16 = round(product / 65536) = 49,020
y = 49,020 / 65536 ≈ 0.748

The exact float answer is 1.0·1.0 + 0.5·(-0.5) = 0.75. The difference is the activation and weight quantization error, not a shift bug.

Common bug

If the output is consistently 65536 times too large, the final shift is missing. If it is 65536 times too small, an extra shift was added. Check the shift before changing the scales. In attention the corresponding shift is 36, not 16, because scores are Q12.

Normalization

RMSNorm without a square-root instruction

RMSNorm scales a row by the reciprocal of its root mean square, then multiplies by a learned gain. In float it is x / sqrt(mean(x²) + ε) · gain. The integer version replaces the square root with a bitwise loop and the division with a rounded integer divide.

The scale bookkeeping

  • x is Q16, so x² is Q32. The sum of squares and the mean stay Q32 in an int64.
  • The epsilon is round(1e-5 · 2³²) = 42950, also Q32.
  • int_isqrt_u64(mean_q32) returns Q16, the same scale as the input.
  • The gain is Q16. Dividing x · gain by the Q16 RMS cancels the gain’s scale and returns Q16.

A worked row

x = [65536, 65536]              // [1.0, 1.0] in Q16
sum_squares = 2 · 65536² = 8,589,934,592
mean_q32 = sum_squares / 2 + 42950 = 4,295,010,246
rms_q16 = isqrt(4,295,010,246) = 65536
y[i] = round(x[i] · gain[i] / rms_q16)
     = round(65536 · 65536 / 65536) = 65536  // [1.0, 1.0]
Common bug

Do not divide by cols after adding epsilon, and do not use a Q16 epsilon. The epsilon belongs in the same Q32 units as the mean. A Q16 epsilon would be far too small after squaring and the norm would behave differently from the float model.

The nonlinearity

GELU as a 4 KB lookup table

The MLP uses the tanh approximation of GELU:

GELU(x) = 0.5 · x · (1 + tanh(0.79788456 · (x + 0.044715 · x³)))

The function is smooth and bounded, so the engine samples it once at load into a Q16 table and interpolates between points at runtime. No transcendental call is needed in the forward pass.

The table geometry

  • Range: -16.0 to +16.0 in Q16.
  • Step: 1/32, or 2048 in Q16 units.
  • Points: 1025, because 32 units per side times 32 steps plus one.
  • Storage: 1025 int32 values, about 4.1 KB.

Below -16 the function is effectively zero, so the lookup returns 0. Above +16 it is effectively the identity, so it returns the input. In between, the index is offset / 2048 and the remainder is offset & 2047. The interpolation shift is 11 because 2¹¹ = 2048.

Common bug

Two off-by-ones live here. The table has 1025 entries, so the last valid index is 1024; the code guards the upper range before indexing. And the interpolation shift is 11, not 12: the step is 1/32 of a Q16 unit, not 1/16.

Checkpoint

Build the table in a test, evaluate it at every grid point, and compare with the float formula. Then evaluate halfway between two grid points and check that the result is between the neighbors. Measure the maximum error; it should be far below the Q16 resolution of the activation stream.

Where the precision changes

Causal attention with Q12 scores and Q15 probabilities

Attention is the part that looks hardest to quantize because it contains an exponential and a division. The engine handles both with tables and fixed-point normalization. The data flow is still the familiar one: project Q, K, and V; score every allowed key against the query; softmax the scores; mix the values.

If any of those words are unfamiliar, read chapter 05 first. It builds attention with ordinary floats and a two-token example. This chapter assumes that picture and explains how each operation is represented in integers.

Quantizing Q, K, and V

wqkv produces a T × 3D Q16 matrix. For each head, the engine slices the head’s head_dim values and quantizes each key and value row with quantize_activation_row. Keys and values are quantized for every position once per head; the query is quantized per position inside the loop. The resulting codes are int8 and the scales are Q16-unit integers.

The score rescale

A dot product of int8 query and key codes is an int32. To turn it into a real score, multiply by the query scale, the key scale, and 1/sqrt(head_dim), all Q16. The real score is the product divided by 2⁴⁸. Softmax wants Q12 nats, so multiply by 2¹²; the engine implements that as a single rounded shift by 36:

real_score = dot · qscale · kscale · inv_sqrt / 2⁴⁸
score_q12  = real_score · 2¹²
           = dot · qscale · kscale · inv_sqrt / 2³⁶

The result is clamped to ±81920 Q12, which is ±20 nats. That is the DI-Exp clipping range. The causal mask is the loop bound j <= t; positions after the query are never computed and their probabilities are zeroed.

DI-Exp softmax

Subtracting the row maximum before exponentiating keeps the arguments non-positive. The engine computes exp(-delta) in Q15 with a 33-entry table of 2^(-k/32), linear interpolation, and a shift by the integer part. The constants are in int_math.h: 5909/4096 ≈ log₂(e) converts nats to bits. The result is normalized with a rounded integer divide so the weights sum to about 32768.

The value sum

Each value code is int8 with a per-token Q16-unit scale. The probability is Q15. The real output is Σ p·v / 2³¹; storing it as Q16 means shifting the int64 accumulator by 15. That is the second shift that is easy to get wrong.

static void attention_q16(TinyGpt *model, const int32_t *qkv) {
  const TinyGptConfig *config = &model->config;
  const int context = config->context;
  const int dim = config->dim;
  const int heads = config->heads;
  const int head_dim = dim / heads;
  const int qkv_stride = dim * 3;

  for (int head = 0; head < heads; ++head) {
    const int head_offset = head * head_dim;

    for (int j = 0; j < context; ++j) {
      const int32_t *key =
          qkv + (size_t)j * qkv_stride + dim + head_offset;
      const int32_t *value =
          qkv + (size_t)j * qkv_stride + dim * 2 + head_offset;
      quantize_activation_row(key, head_dim, model->k8 + (size_t)j * head_dim,
                              &model->k_scale[j]);
      quantize_activation_row(value, head_dim, model->v8 + (size_t)j * head_dim,
                              &model->v_scale[j]);
    }

    for (int t = 0; t < context; ++t) {
      const int32_t *query = qkv + (size_t)t * qkv_stride + head_offset;
      int32_t query_scale = 0;
      quantize_activation_row(query, head_dim, model->q8, &query_scale);

      int32_t row_max = -2147483647;
      for (int j = 0; j <= t; ++j) {
        int32_t dot = 0;
        for (int d = 0; d < head_dim; ++d) {
          dot += (int32_t)model->q8[d] *
                 (int32_t)model->k8[(size_t)j * head_dim + d];
        }
        /*
         * product = dot * qscale * kscale * inv_sqrt_q16. With qscale and
         * kscale in Q16, the real score is product / 2^48. Shift by 36 to
         * land in Q12 (1/4096 nat), which keeps the softmax error well below
         * the Q8 variant's ~1e-3.
         */
        const int64_t product = (int64_t)dot * query_scale *
                                model->k_scale[j] *
                                model->inv_sqrt_head_dim_q16;
        int64_t score = int_shift_round(product, 36);
        if (score > TINY_GPT_SOFTMAX_CLIP_Q12) {
          score = TINY_GPT_SOFTMAX_CLIP_Q12;
        } else if (score < -TINY_GPT_SOFTMAX_CLIP_Q12) {
          score = -TINY_GPT_SOFTMAX_CLIP_Q12;
        }
        model->scores[j] = (int32_t)score;
        if (model->scores[j] > row_max) {
          row_max = model->scores[j];
        }
      }

      int32_t total = 0;
      for (int j = 0; j <= t; ++j) {
        int32_t delta = row_max - model->scores[j];
        if (delta < 0) {
          delta = 0;
        } else if (delta > TINY_GPT_SOFTMAX_CLIP_Q12) {
          delta = TINY_GPT_SOFTMAX_CLIP_Q12;
        }
        const int32_t weight = int_exp_neg_q15_q12(delta);
        model->attn_prob[j] = weight;
        total += weight;
      }
      for (int j = t + 1; j < context; ++j) {
        model->attn_prob[j] = 0;
      }

      if (total > 0) {
        for (int j = 0; j <= t; ++j) {
          model->attn_prob[j] = (int32_t)int_div_round(
              (int64_t)model->attn_prob[j] * INT_Q15_ONE, total);
        }
      } else {
        const int32_t uniform = INT_Q15_ONE / (t + 1);
        for (int j = 0; j <= t; ++j) {
          model->attn_prob[j] = uniform;
        }
      }

      for (int d = 0; d < head_dim; ++d) {
        int64_t accumulator = 0;
        for (int j = 0; j <= t; ++j) {
          accumulator += (int64_t)model->attn_prob[j] *
                         (int64_t)model->v8[(size_t)j * head_dim + d] *
                         model->v_scale[j];
        }
        model->attn[(size_t)t * dim + head_offset + d] =
            (int32_t)int_shift_round(accumulator, 15);
      }
    }
  }
}

Putting it together

The full integer forward pass

The forward pass is deliberately boring once the pieces exist. Embed, then repeat a pre-norm attention block and a pre-norm MLP block, then normalize one last time and project onto the vocabulary.

If you ran the NumPy reference in chapter 09, you have already written this function. The C version is the same sequence with three changes: every matrix multiply is quantized, every norm uses an integer square root, and GELU is a table lookup. The order of operations and the residual adds are identical, which is exactly why the integer version can be verified against the float one.

void tiny_gpt_forward(TinyGpt *model, const int32_t *tokens) {
  if (model == NULL || tokens == NULL) {
    tiny_gpt_error_code = TINY_GPT_ERROR_ARGUMENT;
    return;
  }

  const TinyGptConfig *config = &model->config;
  const int context = config->context;
  const int dim = config->dim;
  const int mlp = config->mlp;
  const int vocab = config->vocab_size;

  /* Embeddings: token and position tables are int8 with Q16 row scales. */
  for (int t = 0; t < context; ++t) {
    int token = tokens[t];
    if (token < 0 || token >= vocab) {
      token = 0;
    }
    const int8_t *token_row = model->token_emb + (size_t)token * dim;
    const int32_t token_scale = model->token_emb_scale[token];
    const int8_t *position_row = model->pos_emb + (size_t)t * dim;
    const int32_t position_scale = model->pos_emb_scale[t];
    for (int d = 0; d < dim; ++d) {
      int64_t value = (int64_t)token_row[d] * token_scale +
                      (int64_t)position_row[d] * position_scale;
      if (value > 2147483647) {
        value = 2147483647;
      } else if (value < -2147483647) {
        value = -2147483647;
      }
      model->x[(size_t)t * dim + d] = (int32_t)value;
    }
  }

  for (int layer = 0; layer < config->layers; ++layer) {
    const TinyGptLayer *weights = &model->layers[layer];

    rmsnorm_q16(model->x, context, dim, weights->g1, model->h);
    matmul_q16(model->h, context, dim, weights->wqkv, weights->wqkv_scale,
               dim * 3, model->q8, model->qkv);
    attention_q16(model, model->qkv);
    matmul_q16(model->attn, context, dim, weights->wo, weights->wo_scale, dim,
               model->q8, model->y);

    for (int i = 0; i < context * dim; ++i) {
      model->x1[i] = model->x[i] + model->y[i];
    }

    rmsnorm_q16(model->x1, context, dim, weights->g2, model->h);
    matmul_q16(model->h, context, dim, weights->w1, weights->w1_scale, mlp,
               model->q8, model->z);

    for (int i = 0; i < context * mlp; ++i) {
      model->gz[i] = gelu_q16(model, model->z[i]);
    }

    matmul_q16(model->gz, context, mlp, weights->w2, weights->w2_scale, dim,
               model->q8, model->m);

    for (int i = 0; i < context * dim; ++i) {
      model->x[i] = model->x1[i] + model->m[i];
    }
  }

  rmsnorm_q16(model->x, context, dim, model->g_final, model->h);
  matmul_q16(model->h, context, dim, model->head, model->head_scale, vocab,
             model->q8, model->logits);

  tiny_gpt_error_code = TINY_GPT_OK;
}

The final projection

The final norm uses g_final, then the head matmul projects T × D onto T × V. Only the last row is needed for generation, but the engine computes all positions because the same function is used for evaluation, probability inspection, and next-token comparisons. A later KV-cache implementation would compute the last row only during decode.

Aliasing rules. The scratch buffers are reused across projections, but no matmul writes its output into its input. If you refactor for memory, preserve that rule or add an explicit temporary. The sampling path uses probs; attention uses scores and attn_prob. Each buffer is sized for the largest use.
Common bug

A missing final norm produces plausible-looking but wrong logits, because the head expects a normalized residual stream. A missing residual produces a model that still runs but cannot represent the identity path. Check the two additions before debugging the quantization.

Checkpoint

From logits to a token

Softmax, temperature, top-k, and xorshift32

The head produces Q16 logits. Generation needs a probability distribution over the vocabulary, a temperature, a top-k cut, and a random draw. Every step is integer-only.

Chapter 07 explains what softmax, temperature, top-k, and sampling mean with ordinary floats. This chapter is the same pipeline with Q15 probabilities, a DI-Exp table, and an integer random generator.

Logits to Q15

The last position’s logits are divided by a Q16 temperature. The code forms (logit_q16 · 65536) / temperature_q16, which is the real ratio stored in Q16, then shifts right by 4 to produce Q12 nats for the same DI-Exp table used by attention. The maximum is subtracted, each delta is clipped to 20 nats, and the weights are normalized to Q15.

softmax_last_q15c · 50 lines
static void softmax_last_q15(TinyGpt *model, int32_t temperature_q16,
                             int32_t *out_q15) {
  const int vocab = model->config.vocab_size;
  const int offset = (model->config.context - 1) * vocab;
  const int32_t *logits = model->logits + offset;

  if (temperature_q16 <= 0) {
    temperature_q16 = 655; /* 0.01 */
  } else if (temperature_q16 < 655) {
    temperature_q16 = 655;
  }

  int32_t maximum = -2147483647;
  for (int i = 0; i < vocab; ++i) {
    const int64_t scaled =
        int_div_round((int64_t)logits[i] * INT_Q16_ONE, temperature_q16);
    /* Q16 (logit / temperature) -> Q12 nats for DI-Exp. */
    const int32_t score = (int32_t)(scaled >> 4);
    model->probs[i] = score;
    if (score > maximum) {
      maximum = score;
    }
  }

  int32_t total = 0;
  for (int i = 0; i < vocab; ++i) {
    int32_t delta = maximum - model->probs[i];
    if (delta < 0) {
      delta = 0;
    } else if (delta > TINY_GPT_SOFTMAX_CLIP_Q12) {
      delta = TINY_GPT_SOFTMAX_CLIP_Q12;
    }
    const int32_t weight = int_exp_neg_q15_q12(delta);
    model->probs[i] = weight;
    total += weight;
  }

  if (total <= 0) {
    const int32_t uniform = INT_Q15_ONE / vocab;
    for (int i = 0; i < vocab; ++i) {
      out_q15[i] = uniform;
    }
    return;
  }

  for (int i = 0; i < vocab; ++i) {
    out_q15[i] = (int32_t)int_div_round(
        (int64_t)model->probs[i] * INT_Q15_ONE, total);
  }
}

tiny_gpt_probabilities calls the same softmax and then doubles each Q15 value to produce Q16 for the host API. The WASM wrapper divides by 65536. If you forget the doubling, every probability is half of what it should be and the sum is 32768 instead of 65536.

Top-k

The sampler keeps the k highest Q15 weights with a partial insertion sort. It skips zero weights, maintains a descending list, and stops at count = k. For a 4096-token vocabulary and k=40 this is trivial compared with the matmuls.

The random draw

A 32-bit xorshift generator supplies the only randomness in the engine. A zero seed is replaced by the golden-ratio constant so the state can never get stuck at zero. The target is (random · total) >> 32, which maps the 32-bit value onto the integer weight range without floating point. The sampler walks the cumulative sum and returns the first candidate whose cumulative weight exceeds the target.

tiny_gpt_samplec · 71 lines
int32_t tiny_gpt_sample(TinyGpt *model, int32_t temperature_q16,
                        int32_t top_k) {
  if (model == NULL) {
    tiny_gpt_error_code = TINY_GPT_ERROR_ARGUMENT;
    return -1;
  }

  const int vocab = model->config.vocab_size;
  softmax_last_q15(model, temperature_q16, model->probs);

  if (top_k < 1) {
    top_k = 1;
  } else if (top_k > vocab) {
    top_k = vocab;
  }

  /*
   * Partial insertion sort: keep the top-k probabilities in descending order.
   * k is small (typically 40), so O(vocab * k) is fine.
   */
  int count = 0;
  for (int id = 0; id < vocab; ++id) {
    const int32_t value = model->probs[id];
    if (value <= 0) {
      continue;
    }
    if (count < top_k) {
      int position = count;
      while (position > 0 && model->top_vals[position - 1] < value) {
        model->top_vals[position] = model->top_vals[position - 1];
        model->top_ids[position] = model->top_ids[position - 1];
        --position;
      }
      model->top_vals[position] = value;
      model->top_ids[position] = id;
      ++count;
    } else if (value > model->top_vals[top_k - 1]) {
      int position = top_k - 1;
      while (position > 0 && model->top_vals[position - 1] < value) {
        model->top_vals[position] = model->top_vals[position - 1];
        model->top_ids[position] = model->top_ids[position - 1];
        --position;
      }
      model->top_vals[position] = value;
      model->top_ids[position] = id;
    }
  }

  if (count <= 0) {
    return 0;
  }

  int64_t total = 0;
  for (int i = 0; i < count; ++i) {
    total += model->top_vals[i];
  }
  if (total <= 0) {
    return model->top_ids[0];
  }

  const uint32_t random = next_random(&model->rng);
  const uint64_t target = ((uint64_t)random * (uint64_t)total) >> 32;
  uint64_t cumulative = 0;
  for (int i = 0; i < count; ++i) {
    cumulative += (uint64_t)model->top_vals[i];
    if (target < cumulative) {
      return model->top_ids[i];
    }
  }
  return model->top_ids[count - 1];
}

End-to-end decode

A tokenizer, a sliding window, and one integer forward pass per token

The engine does not know what a word is. It receives exactly config.context token ids, runs the forward pass, and returns logits. Everything about prompts, chat templates, and stop tokens lives in the host wrapper. Keeping that boundary clean is what lets the same C engine run Alice, Solid 2, or a future checkpoint.

If tokenization is new, chapter 03 explains the vocabulary, embedding lookup, and position table. This chapter is about the host loop that sits above the engine.

The context window

The model has a fixed context length. A prompt shorter than the window is left-padded; a prompt longer than the window keeps only the last T tokens. The position embedding is indexed by the position inside the window, not by the absolute position in the original prompt. This is an inference simplification, and it does not exactly match the trainer: training right-pads fixed-length examples, while generation left-pads so the newest token sits at the last position. A stronger design would use one convention on both sides, or an attention mask that ignores pad tokens.

What crosses the WASM boundary

The engine is compiled to WebAssembly (WASM), the portable bytecode the browser runs. The browser can pass numbers and memory buffers to it, but those values are still just integers. The host wrapper owns the conversion to and from JavaScript.

  • forward: a pointer to T int32 token ids.
  • logits: a pointer to T × V Q16 int32 values.
  • probabilities: a pointer to V Q16 int32 values, converted to float only for display.
  • sample: temperature in Q16, top-k as an integer; the return value is a token id.

The only float value that crosses the core WASM API is the temperature, which the wrapper rounds to Q16 (round(temperature · 65536)). The model arithmetic never crosses back into float. The optional repetition-penalty path is different: it re-scores logits in JavaScript, as the next section explains.

Repetition penalty is a host feature

The Solid 2 wrapper optionally applies a repetition penalty before sampling. That path is implemented in JavaScript because it needs the recent token set and a float logit adjustment; it is not part of the integer engine. If you want a fully integer generation loop, port the penalty into the C sampler or leave it out.

What comes next

Performance, KV cache, and the road to gates

The shipping engine is intentionally simple. It recomputes the full context for every generated token, quantizes activations dynamically, and keeps every intermediate buffer in Q16. That is enough to prove the integer path; it is not the final performance story.

The current cost

For each generated token, the engine runs L blocks over T positions. The matrix work is roughly L·T·(4D² + 2DM) multiply-accumulates, and attention is L·T²·D. With the Solid 2 config that is small on a modern CPU, but it grows linearly in T for the matmuls and quadratically for attention. The implementation has no KV cache, so generating 100 tokens does 100 full passes.

The first optimization: KV cache

During decode, the keys and values for past positions do not change. Quantize them once, store k8, v8, and their scales per layer, and compute only the new query. The block still needs the current token’s residual, but the QKV projection can be reduced to one row, and attention becomes a dot product against the cache. The output is mathematically identical if the cache stores the same quantized values.

A KV cache changes the memory profile: each layer stores T × D/H × H int8 keys and values plus scales. For Solid 2 that is small; for a larger model it becomes the dominant memory cost. This is why the current simple version is a good teaching reference first.

From integers to gates

Every operation in this page has a hardware shape. An 8-bit adder is a handful of gates. A comparator is a tree of them. A shift by a constant is wiring. A multiply by a constant can become a shift-add network or a ROM. A GELU or exp lookup is BRAM plus an address mux. The quantized model is already a fixed dataflow; the lowering problem is scheduling that graph onto gates and memory, not inventing a new model.

The repository’s gate compiler already lowers small symbol-classifier circuits to a 16-gate vocabulary. Lowering a full transformer adds wider arithmetic, a matrix-tile schedule, on-chip memory planning, and token-by-token control. Those are engineering problems, not reasons the idea fails.

What changes for an FPGA

  • Dynamic per-row activation quantization needs a max-reduction and a reciprocal at runtime. An FPGA implementation may prefer static or per-tile scales, or a small divider pipeline.
  • The GELU and DI-Exp tables map naturally to block RAM (BRAM); the address generation and interpolation are the work.
  • Attention is a systolic or tiled array problem; the causal mask lets you skip work, but the schedule must not stall. A systolic array is a grid of processing elements that passes data between neighbours, which suits repeated matrix multiplication.
  • The model is fixed at synthesis time. Changing weights means resynthesis or a memory-load path.

The honest status is: integer-only inference in WebAssembly is working; the gate compiler is a prototype for small circuits; a gate-lowered GPT and an FPGA implementation are the roadmap. The deep dive stops at the integer engine because that is the part that ships.

Checkpoint

Measure tokens per second for a fixed prompt, then sketch a KV-cache layout with k8, v8, k_scale, and v_scale per layer. Estimate the memory for Solid 2 atT=256. Then pick one integer operation and write down its gate-level shape.

  if (b <= 0) {
    return 0;
  }
  if (a >= 0) {
    return (a + b / 2) / b;
  }
  return -((-a + b / 2) / b);
}

static inline int64_t int_shift_round(int64_t a, int shift) {
  if (shift <= 0) {
    return a;
  }
  return (a + ((int64_t)1 << (shift - 1))) >> shift;
}

/* Floor of sqrt(n), integer-only. */
static inline uint64_t int_isqrt_u64(uint64_t n) {
  uint64_t result = 0;
  uint64_t bit = (uint64_t)1 << 62;
  while (bit > n) {
    bit >>= 2;
  }
  while (bit != 0) {
    if (n >= result + bit) {
      n -= result + bit;
      result = (result >> 1) + bit;
    } else {
      result >>= 1;
    }
    bit >>= 2;
  }
  return result;
}

/*
 * exp(-x) in Q15 for x >= 0 in Q12 (1/4096 nat resolution).
 *
 * The exponent is clamped to 20 nats by the callers (the paper's DI-Exp
 * clipping range). Values beyond the Q15 resolution return 0.
 */
static inline int32_t int_exp_neg_q15_q12(int32_t x_q12) {
  if (x_q12 <= 0) {
    return INT_Q15_ONE;
  }
  const int32_t y_q12 = (int32_t)(((int64_t)x_q12 * 5909) >> 12);
  const int32_t integer_part = y_q12 >> 12;
  if (integer_part >= 15) {
    return 0;
  }
  const int32_t fraction = y_q12 & 4095;
  const int32_t index = fraction >> 7;
  const int32_t remainder = fraction & 127;
  const int32_t a = INT_TWO_POW_NEG_Q15[index];
  const int32_t b = INT_TWO_POW_NEG_Q15[index + 1];
  const int32_t value = a - (((a - b) * remainder) >> 7);
  return value >> integer_part;
}

/*
 * Load-time checkpoint conversion. Floating point is confined to this file:
 * it turns the trained float32 weights into int8 matrices with Q16 scales,
 * Q16 norm gains and a Q16 GELU lookup table. tiny_gpt_infer.c only sees the
 * resulting integers.
 */

static int32_t q16_from_float(float value) {
  const float scaled = roundf(value * 65536.0f);
  if (scaled > 2147483647.0f) {
    return 2147483647;
  }
  if (scaled < -2147483648.0f) {
    return (-2147483647 - 1);
  }
  return (int32_t)scaled;
}

static int32_t scale_q16_from_float(float scale) {
  if (!(scale > 0.0f)) {
    return 0;
  }
  const float scaled = roundf(scale * 65536.0f);
  if (scaled < 1.0f) {
    return 1;
  }
  if (scaled > 2147483647.0f) {
    return 2147483647;
  }
  return (int32_t)scaled;
}

static int8_t quantize_value(float value, float inverse) {
  float scaled = roundf(value * inverse);
  if (scaled > 127.0f) {
    scaled = 127.0f;
  } else if (scaled < -127.0f) {
    scaled = -127.0f;
  }
  return (int8_t)scaled;
}

/* One int8 scale per row (embedding lookup tables). */
static void quantize_rows(const float *src, int rows, int cols, int8_t *dst,
                          int32_t *scales) {
  for (int row = 0; row < rows; ++row) {
    const float *source = src + (size_t)row * cols;
    int8_t *target = dst + (size_t)row * cols;
    float max_abs = 0.0f;
    for (int col = 0; col < cols; ++col) {
      const float magnitude = fabsf(source[col]);
      if (magnitude > max_abs) {
        max_abs = magnitude;
      }
    }
    if (max_abs <= 0.0f) {
      memset(target, 0, (size_t)cols);
      scales[row] = 0;
      continue;
    }
    scales[row] = scale_q16_from_float(max_abs / 127.0f);
    const float inverse = 127.0f / max_abs;
    for (int col = 0; col < cols; ++col) {
      target[col] = quantize_value(source[col], inverse);
    }
  }
}

/* One int8 scale per output column (linear projections). */
static void quantize_columns(const float *src, int rows, int cols, int8_t *dst,
                             int32_t *scales) {
  for (int col = 0; col < cols; ++col) {
    float max_abs = 0.0f;
    for (int row = 0; row < rows; ++row) {
      const float magnitude = fabsf(src[(size_t)row * cols + col]);
      if (magnitude > max_abs) {
        max_abs = magnitude;
      }
    }
    if (max_abs <= 0.0f) {
      scales[col] = 0;
      for (int row = 0; row < rows; ++row) {
        dst[(size_t)row * cols + col] = 0;
      }
      continue;
    }
    scales[col] = scale_q16_from_float(max_abs / 127.0f);
    const float inverse = 127.0f / max_abs;
    for (int row = 0; row < rows; ++row) {
      const size_t index = (size_t)row * cols + col;
      dst[index] = quantize_value(src[index], inverse);
    }
  }
}

static void quantize_gain(const float *src, int length, int32_t *dst) {
  for (int i = 0; i < length; ++i) {
    dst[i] = q16_from_float(src[i]);
  }
}

static void build_gelu_lut(int32_t *lut) {
  for (int i = 0; i < TINY_GPT_GELU_POINTS; ++i) {
    const float x = -16.0f + (float)i / 32.0f;
    const float inner = 0.7978845608028654f * (x + 0.044715f * x * x * x);
    const float value = 0.5f * x * (1.0f + tanhf(inner));
    lut[i] = q16_from_float(value);
  }
}

  model->config.layers = layers;
  model->config.heads = heads;
  model->config.mlp = mlp;
  model->inv_sqrt_head_dim_q16 = inverse_sqrt_q16(dim / heads);
  model->rng = 0x9e3779b9u;

  const float *cursor = packed_weights;
  const float *token_emb = cursor;
  cursor += (size_t)vocab_size * dim;
  const float *pos_emb = cursor;
  cursor += (size_t)context * dim;
  const float *g_final = cursor;
  cursor += dim;

  model->token_emb = allocate_zero((size_t)vocab_size * dim, sizeof(int8_t));
  model->token_emb_scale = allocate_zero((size_t)vocab_size, sizeof(int32_t));
  model->pos_emb = allocate_zero((size_t)context * dim, sizeof(int8_t));
  model->pos_emb_scale = allocate_zero((size_t)context, sizeof(int32_t));
  model->head = allocate_zero((size_t)dim * vocab_size, sizeof(int8_t));
  model->head_scale = allocate_zero((size_t)vocab_size, sizeof(int32_t));
  model->g_final = allocate_zero((size_t)dim, sizeof(int32_t));
  model->layers = allocate_zero((size_t)layers, sizeof(TinyGptLayer));

  if (model->token_emb == NULL || model->token_emb_scale == NULL ||
      model->pos_emb == NULL || model->pos_emb_scale == NULL ||
      model->head == NULL || model->head_scale == NULL ||
      model->g_final == NULL || model->layers == NULL) {
    tiny_gpt_error_code = TINY_GPT_ERROR_ALLOC;
    tiny_gpt_destroy(model);
    return NULL;
  }

  quantize_rows(token_emb, vocab_size, dim, model->token_emb,
                model->token_emb_scale);
  quantize_rows(pos_emb, context, dim, model->pos_emb, model->pos_emb_scale);
  quantize_gain(g_final, dim, model->g_final);

  /*
   * The output head is the tied token embedding, transposed to dim x vocab.
   * Reuse the row-quantized values and scales so the two paths stay identical.
   */
  for (int token = 0; token < vocab_size; ++token) {
    model->head_scale[token] = model->token_emb_scale[token];
    for (int d = 0; d < dim; ++d) {
      model->head[(size_t)d * vocab_size + token] =
          model->token_emb[(size_t)token * dim + d];
    }
  }

  for (int layer = 0; layer < layers; ++layer) {
    if (!allocate_layer_weights(&model->layers[layer], dim, mlp, &cursor)) {
      tiny_gpt_error_code = TINY_GPT_ERROR_ALLOC;
      tiny_gpt_destroy(model);
      return NULL;
    }
  }

  if (!allocate_scratch(model)) {
    tiny_gpt_error_code = TINY_GPT_ERROR_ALLOC;
    tiny_gpt_destroy(model);
    return NULL;
  }

  build_gelu_lut(model->gelu_lut);

  return model;
}

static uint32_t next_random(uint32_t *state) {
  uint32_t value = *state;
  value ^= value << 13;
  value ^= value >> 17;
  value ^= value << 5;
  *state = value;
  return value;
}

/*
 * Dynamically quantizes one activation row (Q16) to int8. The returned scale
 * is in Q16 units, so `value ~= q8 * scale / 65536`.
 */
static void quantize_activation_row(const int32_t *src, int count, int8_t *dst,
                                    int32_t *scale_out) {
  int32_t max_abs = 0;
  for (int i = 0; i < count; ++i) {
    const int32_t value = src[i];
    const int32_t magnitude = value < 0 ? -value : value;
    if (magnitude > max_abs) {
      max_abs = magnitude;
    }
  }

  if (max_abs == 0) {
    *scale_out = 0;
    memset(dst, 0, (size_t)count);
    return;
  }
  if (max_abs <= 127) {
    *scale_out = 1;
    for (int i = 0; i < count; ++i) {
      dst[i] = (int8_t)src[i];
    }
    return;
  }

  *scale_out = (max_abs + 63) / 127;
  for (int i = 0; i < count; ++i) {
    int64_t quantized = int_div_round((int64_t)src[i] * 127, max_abs);
    if (quantized > 127) {
      quantized = 127;
    } else if (quantized < -127) {
      quantized = -127;
    }
    dst[i] = (int8_t)quantized;
  }
}

/*
 * DI-MatMul: per-token int8 activations, int8 weights with per-column Q16
 * scales, int32 accumulation, single int64 requantization to Q16 output.
 */
static void matmul_q16(const int32_t *x, int rows, int cols,
                       const int8_t *weights, const int32_t *weight_scale,
                       int out_cols, int8_t *scratch, int32_t *out) {
  for (int row = 0; row < rows; ++row) {
    int32_t activation_scale = 0;
    quantize_activation_row(x + (size_t)row * cols, cols, scratch,
                            &activation_scale);
    int32_t *target = out + (size_t)row * out_cols;
    for (int j = 0; j < out_cols; ++j) {
      int32_t accumulator = 0;
      for (int k = 0; k < cols; ++k) {
        accumulator +=
            (int32_t)scratch[k] * (int32_t)weights[(size_t)k * out_cols + j];
      }
      const int64_t product =
          (int64_t)accumulator * activation_scale * weight_scale[j];
      target[j] = (int32_t)int_shift_round(product, 16);
    }
  }
}

/* DI-Norm: int64 sum of squares, integer sqrt, Q16 reciprocal and gain. */
static void rmsnorm_q16(const int32_t *x, int rows, int cols,
                        const int32_t *gain, int32_t *out) {
  /* round(1e-5 * 2^32), matching the float path's epsilon. */
  const int64_t epsilon_q32 = 42950;
  for (int row = 0; row < rows; ++row) {
    const int32_t *source = x + (size_t)row * cols;
    int32_t *target = out + (size_t)row * cols;
    int64_t sum_squares = 0;
    for (int i = 0; i < cols; ++i) {
      const int64_t value = source[i];
      sum_squares += value * value;
    }
    const int64_t mean_q32 = sum_squares / cols + epsilon_q32;
    int64_t rms_q16 = (int64_t)int_isqrt_u64((uint64_t)mean_q32);
    if (rms_q16 == 0) {
      rms_q16 = 1;
    }
    for (int i = 0; i < cols; ++i) {
      const int64_t scaled = (int64_t)source[i] * gain[i];
      target[i] = (int32_t)int_div_round(scaled, rms_q16);
    }
  }
}

/* Integer GELU: Q16 lookup table with linear interpolation. */
static int32_t gelu_q16(const TinyGpt *model, int32_t x) {
  if (x <= TINY_GPT_GELU_MIN_Q16) {
    return 0;
  }
  if (x >= TINY_GPT_GELU_MAX_Q16) {
    return x;
  }
  const int32_t offset = x - TINY_GPT_GELU_MIN_Q16;
  const int index = offset / TINY_GPT_GELU_STEP_Q16;
  const int32_t remainder = offset & (TINY_GPT_GELU_STEP_Q16 - 1);
  const int32_t a = model->gelu_lut[index];
  const int32_t b = model->gelu_lut[index + 1];
  /* STEP_Q16 is 2048 = 1 << 11, so the interpolation shift is 11. */
  return a + (int32_t)(((int64_t)(b - a) * remainder) >> 11);
}

/*
 * Integer attention. Q/K/V are quantized per head and per token, scores use
 * int8 dot products, DI-Exp with clipping produces Q15 probabilities, and the
 * value aggregation uses the corrected P * V indexing (sum over keys).
 */
static void attention_q16(TinyGpt *model, const int32_t *qkv) {
  const TinyGptConfig *config = &model->config;
  const int context = config->context;
  const int dim = config->dim;
  const int heads = config->heads;
  const int head_dim = dim / heads;
  const int qkv_stride = dim * 3;

  for (int head = 0; head < heads; ++head) {
    const int head_offset = head * head_dim;

    for (int j = 0; j < context; ++j) {
      const int32_t *key =
          qkv + (size_t)j * qkv_stride + dim + head_offset;
      const int32_t *value =
          qkv + (size_t)j * qkv_stride + dim * 2 + head_offset;
      quantize_activation_row(key, head_dim, model->k8 + (size_t)j * head_dim,
                              &model->k_scale[j]);
      quantize_activation_row(value, head_dim, model->v8 + (size_t)j * head_dim,
                              &model->v_scale[j]);
    }

    for (int t = 0; t < context; ++t) {
      const int32_t *query = qkv + (size_t)t * qkv_stride + head_offset;
      int32_t query_scale = 0;
      quantize_activation_row(query, head_dim, model->q8, &query_scale);

      int32_t row_max = -2147483647;
      for (int j = 0; j <= t; ++j) {
        int32_t dot = 0;
        for (int d = 0; d < head_dim; ++d) {
          dot += (int32_t)model->q8[d] *
                 (int32_t)model->k8[(size_t)j * head_dim + d];
        }
        /*
         * product = dot * qscale * kscale * inv_sqrt_q16. With qscale and
         * kscale in Q16, the real score is product / 2^48. Shift by 36 to
         * land in Q12 (1/4096 nat), which keeps the softmax error well below
         * the Q8 variant's ~1e-3.
         */
        const int64_t product = (int64_t)dot * query_scale *
                                model->k_scale[j] *
                                model->inv_sqrt_head_dim_q16;
        int64_t score = int_shift_round(product, 36);
        if (score > TINY_GPT_SOFTMAX_CLIP_Q12) {
          score = TINY_GPT_SOFTMAX_CLIP_Q12;
        } else if (score < -TINY_GPT_SOFTMAX_CLIP_Q12) {
          score = -TINY_GPT_SOFTMAX_CLIP_Q12;
        }
        model->scores[j] = (int32_t)score;
        if (model->scores[j] > row_max) {
          row_max = model->scores[j];
        }
      }

      int32_t total = 0;
      for (int j = 0; j <= t; ++j) {
        int32_t delta = row_max - model->scores[j];
        if (delta < 0) {
          delta = 0;
        } else if (delta > TINY_GPT_SOFTMAX_CLIP_Q12) {
          delta = TINY_GPT_SOFTMAX_CLIP_Q12;
        }
        const int32_t weight = int_exp_neg_q15_q12(delta);
        model->attn_prob[j] = weight;
        total += weight;
      }
      for (int j = t + 1; j < context; ++j) {
        model->attn_prob[j] = 0;
      }

      if (total > 0) {
        for (int j = 0; j <= t; ++j) {
          model->attn_prob[j] = (int32_t)int_div_round(
              (int64_t)model->attn_prob[j] * INT_Q15_ONE, total);
        }
      } else {
        const int32_t uniform = INT_Q15_ONE / (t + 1);
        for (int j = 0; j <= t; ++j) {
          model->attn_prob[j] = uniform;
        }
      }

      for (int d = 0; d < head_dim; ++d) {
        int64_t accumulator = 0;
        for (int j = 0; j <= t; ++j) {
          accumulator += (int64_t)model->attn_prob[j] *
                         (int64_t)model->v8[(size_t)j * head_dim + d] *
                         model->v_scale[j];
        }
        model->attn[(size_t)t * dim + head_offset + d] =
            (int32_t)int_shift_round(accumulator, 15);
      }
    }
  }
}

/* Integer softmax over the last position. Writes vocab Q15 probabilities. */
static void softmax_last_q15(TinyGpt *model, int32_t temperature_q16,
                             int32_t *out_q15) {
  const int vocab = model->config.vocab_size;
  const int offset = (model->config.context - 1) * vocab;
  const int32_t *logits = model->logits + offset;

  if (temperature_q16 <= 0) {
    temperature_q16 = 655; /* 0.01 */
  } else if (temperature_q16 < 655) {
    temperature_q16 = 655;
  }

  int32_t maximum = -2147483647;
  for (int i = 0; i < vocab; ++i) {
    const int64_t scaled =
        int_div_round((int64_t)logits[i] * INT_Q16_ONE, temperature_q16);
    /* Q16 (logit / temperature) -> Q12 nats for DI-Exp. */
    const int32_t score = (int32_t)(scaled >> 4);
    model->probs[i] = score;
    if (score > maximum) {
      maximum = score;
    }
  }

  int32_t total = 0;
  for (int i = 0; i < vocab; ++i) {
    int32_t delta = maximum - model->probs[i];
    if (delta < 0) {
      delta = 0;
    } else if (delta > TINY_GPT_SOFTMAX_CLIP_Q12) {
      delta = TINY_GPT_SOFTMAX_CLIP_Q12;
    }
    const int32_t weight = int_exp_neg_q15_q12(delta);
    model->probs[i] = weight;
    total += weight;
  }

  if (total <= 0) {
    const int32_t uniform = INT_Q15_ONE / vocab;
    for (int i = 0; i < vocab; ++i) {
      out_q15[i] = uniform;
    }
    return;
  }

  for (int i = 0; i < vocab; ++i) {
    out_q15[i] = (int32_t)int_div_round(
        (int64_t)model->probs[i] * INT_Q15_ONE, total);
  }
}

void tiny_gpt_forward(TinyGpt *model, const int32_t *tokens) {
  if (model == NULL || tokens == NULL) {
    tiny_gpt_error_code = TINY_GPT_ERROR_ARGUMENT;
    return;
  }

  const TinyGptConfig *config = &model->config;
  const int context = config->context;
  const int dim = config->dim;
  const int mlp = config->mlp;
  const int vocab = config->vocab_size;

  /* Embeddings: token and position tables are int8 with Q16 row scales. */
  for (int t = 0; t < context; ++t) {
    int token = tokens[t];
    if (token < 0 || token >= vocab) {
      token = 0;
    }
    const int8_t *token_row = model->token_emb + (size_t)token * dim;
    const int32_t token_scale = model->token_emb_scale[token];
    const int8_t *position_row = model->pos_emb + (size_t)t * dim;
    const int32_t position_scale = model->pos_emb_scale[t];
    for (int d = 0; d < dim; ++d) {
      int64_t value = (int64_t)token_row[d] * token_scale +
                      (int64_t)position_row[d] * position_scale;
      if (value > 2147483647) {
        value = 2147483647;
      } else if (value < -2147483647) {
        value = -2147483647;
      }
      model->x[(size_t)t * dim + d] = (int32_t)value;
    }
  }

  for (int layer = 0; layer < config->layers; ++layer) {
    const TinyGptLayer *weights = &model->layers[layer];

    rmsnorm_q16(model->x, context, dim, weights->g1, model->h);
    matmul_q16(model->h, context, dim, weights->wqkv, weights->wqkv_scale,
               dim * 3, model->q8, model->qkv);
    attention_q16(model, model->qkv);
    matmul_q16(model->attn, context, dim, weights->wo, weights->wo_scale, dim,
               model->q8, model->y);

    for (int i = 0; i < context * dim; ++i) {
      model->x1[i] = model->x[i] + model->y[i];
    }

    rmsnorm_q16(model->x1, context, dim, weights->g2, model->h);
    matmul_q16(model->h, context, dim, weights->w1, weights->w1_scale, mlp,
               model->q8, model->z);

    for (int i = 0; i < context * mlp; ++i) {
      model->gz[i] = gelu_q16(model, model->z[i]);
    }

    matmul_q16(model->gz, context, mlp, weights->w2, weights->w2_scale, dim,
               model->q8, model->m);

    for (int i = 0; i < context * dim; ++i) {
      model->x[i] = model->x1[i] + model->m[i];
    }
  }

  rmsnorm_q16(model->x, context, dim, model->g_final, model->h);
  matmul_q16(model->h, context, dim, model->head, model->head_scale, vocab,
             model->q8, model->logits);

  tiny_gpt_error_code = TINY_GPT_OK;
}

int32_t tiny_gpt_sample(TinyGpt *model, int32_t temperature_q16,
                        int32_t top_k) {
  if (model == NULL) {
    tiny_gpt_error_code = TINY_GPT_ERROR_ARGUMENT;
    return -1;
  }

  const int vocab = model->config.vocab_size;
  softmax_last_q15(model, temperature_q16, model->probs);

  if (top_k < 1) {
    top_k = 1;
  } else if (top_k > vocab) {
    top_k = vocab;
  }

  /*
   * Partial insertion sort: keep the top-k probabilities in descending order.
   * k is small (typically 40), so O(vocab * k) is fine.
   */
  int count = 0;
  for (int id = 0; id < vocab; ++id) {
    const int32_t value = model->probs[id];
    if (value <= 0) {
      continue;
    }
    if (count < top_k) {
      int position = count;
      while (position > 0 && model->top_vals[position - 1] < value) {
        model->top_vals[position] = model->top_vals[position - 1];
        model->top_ids[position] = model->top_ids[position - 1];
        --position;
      }
      model->top_vals[position] = value;
      model->top_ids[position] = id;
      ++count;
    } else if (value > model->top_vals[top_k - 1]) {
      int position = top_k - 1;
      while (position > 0 && model->top_vals[position - 1] < value) {
        model->top_vals[position] = model->top_vals[position - 1];
        model->top_ids[position] = model->top_ids[position - 1];
        --position;
      }
      model->top_vals[position] = value;
      model->top_ids[position] = id;
    }
  }

  if (count <= 0) {
    return 0;
  }

  int64_t total = 0;
  for (int i = 0; i < count; ++i) {
    total += model->top_vals[i];
  }
  if (total <= 0) {
    return model->top_ids[0];
  }

  const uint32_t random = next_random(&model->rng);
  const uint64_t target = ((uint64_t)random * (uint64_t)total) >> 32;
  uint64_t cumulative = 0;
  for (int i = 0; i < count; ++i) {
    cumulative += (uint64_t)model->top_vals[i];
    if (target < cumulative) {
      return model->top_ids[i];
    }
  }
  return model->top_ids[count - 1];
}

GPTGenerative pre-trained transformer. A decoder-only model trained to predict the next token, then used to generate text one token at a time.

VocabularyThe fixed set of tokens a model knows. Its size is V. A checkpoint and its tokenizer are a pair.
TokenizerThe separate program that converts text to token ids and back. It is not part of the C inference engine.
BPEByte-pair encoding. A tokenizer that starts from bytes and repeatedly merges frequent adjacent pairs.
Token idAn index into the embedding table. Id 400 is not 'twice' id 200; the number has no arithmetic meaning.
EmbeddingA learned vector that represents a token (or a position). The embedding table is a lookup table of shape [V, D].
Position embeddingA learned vector added to each token embedding so the model can tell positions apart.
Model dimension (D)The number of values in each token's vector. Also called the model width or hidden size.
Context window (T)The fixed number of token positions the model reads in one forward pass. Older tokens fall out of the window.
LogitsUnnormalized scores over the vocabulary. Softmax turns logits into probabilities.
SoftmaxThe function exp(z[i]) / sum(exp(z[j])). It turns arbitrary scores into positive values that sum to one.
TemperatureA divisor applied to logits before softmax. Lower values sharpen the distribution; higher values flatten it.
Top-kKeep only the k highest-probability candidates before sampling, then renormalize.
Greedy decodingAlways choose the highest-probability token. Deterministic, but often repetitive.
AttentionA mechanism that lets each position read information from allowed earlier positions using query/key similarity and a weighted sum of values.
Query, key, value (Q/K/V)Three learned projections of a token vector. The query asks what is needed, the key advertises what is available, and the value carries the content.
HeadOne independent attention computation on a slice of the model dimension. Multi-head attention runs several in parallel.
Causal maskThe rule that position t may only attend to positions j <= t. It prevents the model from seeing the future during training.
Residual streamThe [T, D] matrix that runs through the whole model. Each sublayer adds its output to it instead of replacing it.
Residual connectionThe x = x + sublayer(x) pattern. It preserves information and gives gradients a short path during training.
RMSNormRoot-mean-square normalization. Divides a row by the RMS of its values and multiplies by a learned gain.
MLPMulti-layer perceptron, also called the feed-forward network. Expands each position to width M, applies GELU, and projects back to D.
GELUGaussian error linear unit. A smooth nonlinearity; here the tanh approximation, implemented as a lookup table.
ParameterA learned number in a weight matrix, gain, or embedding table. Training adjusts parameters; inference only reads them.
Tied embeddingsUsing the token embedding matrix, transposed, as the output head. It saves parameters and aligns input and output token spaces.
TrainingThe phase that measures prediction error and adjusts every parameter with gradients. It needs floating point.
InferenceRunning a fixed trained model on new input. It is deterministic and can be integer-only.
LossA single number measuring how wrong the model is. Language models use cross-entropy on the correct next token.
Cross-entropyThe loss -log(p[target]). Confident correct predictions have low loss; unlikely correct predictions have high loss.
Perplexityexp(loss). Roughly the number of equally likely tokens the model is choosing among.
GradientThe derivative of the loss with respect to a parameter: which way, and how strongly, to change it.
BackpropagationApplying the chain rule backwards through the network to compute every gradient efficiently.
OptimizerThe rule that turns gradients into weight updates. This project uses AdamW.
Learning rateThe size of an optimizer step. Too large diverges; too small learns slowly.
Step / batch / epochOne update / the examples behind one update / one pass over the training set.
OverfittingMemorizing training data so training loss falls while validation loss rises.
Q16Fixed-point value with 16 fractional bits; 65536 means 1.0.
Q15Fixed-point value with 15 fractional bits; 32768 means 1.0.
Q12Fixed-point value with 12 fractional bits; 4096 means 1.0.
QuantizationStoring a real value as a small integer code plus a scale. Real ≈ code × scale / 65536 for Q16 scales.
ScaleThe multiplier that maps an int8 code back to a real value. Weights use per-column scales; embeddings use per-row scales.
RequantizeConvert an accumulator back to a fixed-point scale with a rounded shift.
AccumulatorThe integer sum of many products before scaling. Here it is int32 for int8 dot products.
DI-ExpA table-driven integer approximation of exp(-x), used for attention and softmax.
KV cacheReusing past keys and values instead of recomputing the whole context for every generated token.
DeterministicGiven the same input, weights, and seed, the engine returns exactly the same output. The sampler is deterministic in this sense.

I. The fifteen-point checklist

  1. Text becomes ids with the exact tokenizer that was trained with the checkpoint.
  2. Token embeddings and position embeddings are added, not concatenated.
  3. Every block has the same shape: norm, attention, add, norm, MLP, add.
  4. The causal mask only allows j ≤ t; the future is never computed.
  5. Weights are packed in the exact order, with every linear matrix transposed.
  6. Weight scales are Q16 fractions; activation scales are Q16-unit integers.
  7. Every dot product accumulates in int32 and requantizes in int64.
  8. Matmul shifts by 16; attention scores shift by 36; V sums shift by 15.
  9. RMSNorm uses a Q32 epsilon and an integer square root.
  10. GELU uses 1025 Q16 entries over [-16, 16] with a shift of 11.
  11. Attention only computes j ≤ t.
  12. Softmax subtracts the max and clamps deltas to 20 nats.
  13. Q15 probabilities sum to 32768; the host API converts to Q16 by doubling.
  14. Sampling is seeded, deterministic, and independent of the host RNG.
  15. The float reference and the integer engine agree on top-1 and top-5 for your test prompts.
The claim to keep. This page teaches integer-only inference. It does not claim bit-identical output to float, a KV cache, or an FPGA implementation. Those are separate milestones, and the field notes track them honestly.
